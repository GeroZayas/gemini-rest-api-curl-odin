Para abril de 2026, la librería estándar `core:time` en Odin sigue siendo el pilar fundamental para el manejo de cronometría. Aunque la API de Odin es extremadamente estable, el uso de estos procedimientos se ha consolidado en torno a patrones de "alta precisión" y "medición de frames".

Aquí tienes los procedimientos más útiles y usados actualmente:

### 1. `time.now()`

Es el estándar absoluto. Devuelve un `Time` (que bajo el capó es un struct con un valor `tick` de 64 bits). Es la base para cualquier medición de tiempo en el motor o aplicación.

- **Uso típico:** Capturar el inicio y el fin de un proceso.

### 2. `time.diff(start, end)`

Es el procedimiento que más verás en cualquier bucle de juego o sistema de benchmarks. Devuelve un `Duration`, que es un `i64` que representa nanosegundos.

- **Por qué se usa:** Es la forma más eficiente de calcular el tiempo transcurrido sin asignar memoria ni realizar conversiones innecesarias.

### 3. `time.duration_seconds(d)` / `time.duration_milliseconds(d)`

Después de obtener un `Duration` con `time.diff`, casi siempre querrás convertirlo a una unidad legible por humanos o para lógica de juego.

- **Diferencia clave:** En 2026, se prefiere `duration_seconds` (que devuelve `f64`) para cálculos de _Delta Time_ en motores gráficos, ya que es el estándar para mover objetos en el espacio 3D.

### 4. `time.tick_now()` y `time.tick_since(t)`

Aunque `time.now()` es común, en sistemas de muy baja latencia, los desarrolladores avanzados usan `tick_now()`.

- **La diferencia:** Mientras que `time.now()` es una abstracción de alto nivel, `tick_now()` accede directamente a los contadores de alta resolución del sistema operativo (como `QueryPerformanceCounter` en Windows o `clock_gettime` en POSIX). Es ligeramente más rápido y menos propenso a cambios de zona horaria o sincronizaciones de NTP.

### 5. `time.sleep(duration)`

Fundamental para hilos de fondo, trabajadores (workers) o para limitar el framerate sin abusar de la CPU.

- **Nota de uso:** En aplicaciones de alto rendimiento, se suele usar en combinación con una espera activa (spin-lock) para no consumir el 100% de la CPU pero manteniendo la precisión necesaria.

---

### Ejemplo de patrón común en 2026 (El "Game Loop"):

```odin
import "core:time"
import "core:fmt"

main :: proc() {
    start := time.now()

    // ... hacer el trabajo ...

    elapsed := time.diff(start, time.now())
    dt := time.duration_seconds(elapsed)

    fmt.printf("El frame tardó %f segundos\n", dt)
}
```

### ¿Qué ha cambiado/es relevante en 2026?

1.  **Seguridad de hilos:** Se ha enfatizado mucho el uso de `time.now()` en lugar de leer relojes del sistema directamente, para evitar problemas en arquitecturas ARM donde la lectura de ciertos registros puede ser problemática si no se hace a través de las abstracciones de `core:time`.
2.  **`time.Duration` como `i64`:** Se mantiene como un entero, lo cual es vital para el rendimiento en Odin. Se desalienta el uso de _floating point_ para el almacenamiento de tiempo, dejándolo solo para la presentación final (`duration_seconds`).
3.  **Benchmark simple:** Muchos desarrolladores siguen usando `time.now()` para crear sus propios mini-profilers, ya que es extremadamente "barato" en términos de ciclos de CPU.

**Consejo profesional:** Si estás trabajando en sistemas que requieren alta precisión (como audio o renderizado de baja latencia), evita convertir a `f64` hasta el último paso posible de tus cálculos para mantener la precisión de los `nanosegundos` (i64).
